## Product design

### Goals / Non-goals

**Goals:**
- Ship a first version of `MSPbotsAIFramework/plaid-mcp` that lets an AI agent, acting on behalf of one MSPbots tenant, read Plaid-linked bank account data for an already-linked or newly-linked end customer: account list and balances, routing/account numbers (Auth), transactions, identity, investment holdings, and liabilities.
- Let the agent kick off linking a **new** bank account on behalf of an end customer using Plaid's Hosted Link (a URL Plaid itself serves — no embedded Link SDK required from this MCP) and check whether that linking session has completed.
- Let the agent remove (unlink) an Item on explicit confirmation.
- Every call authenticates with the caller's own Plaid `client_id`/`secret`/environment carried as request headers; one running server instance safely serves multiple MSPbots tenants/Plaid developer accounts concurrently (same multi-tenant isolation contract as every other first-party MCP in this org).

**Non-goals (this version):**
- No webhook receiver. Plaid's push notifications (`SESSION_FINISHED`, `TRANSACTIONS_UPDATES_AVAILABLE`, …) require a publicly reachable callback URL; this MCP service is not exposed to the public internet (same constraint as every other vendor MCP in this org). The agent discovers Hosted Link completion and new-transaction availability by polling, not by webhook.
- No embedded (client-side SDK) Link flow — only Hosted Link, which fits a server-only, AI-agent-driven integration. Embedding Plaid Link's JS/mobile SDK would require a UI surface this MCP does not have.
- No Payments/Transfer, Income, or Monitor products — the ticket names no specific capability, and these are separate, more specialized Plaid products (money movement, income verification, fraud signals) that would each need their own design and explicit sign-off before an agent gets write access to money movement. Flagged as a follow-up, not built here.
- No write access to account data itself (Plaid does not offer that — all products here are read, plus the Link/Item lifecycle operations needed to create and remove a connection).

### Acceptance criteria AC1..AC10

- **AC1**: Given valid `X-Plaid-Client-Id`/`X-Plaid-Secret`/`X-Plaid-Env` headers and a list of Plaid products, when the agent calls the create-link-session tool, then it receives a `hosted_link_url` the end customer can open in a browser to link their bank, plus a `link_token` to check on that session later.
- **AC2**: Given a missing or invalid credential header, when any tool is called, then the tool call fails with a structured `unauthorized` error (HTTP 401 at the transport layer) that does not echo the invalid header value back.
- **AC3**: Given a Hosted Link session the end customer has not yet completed, when the agent polls the link-session-status tool, then it reports a pending status (no `public_token` yet); once the customer finishes, the same call returns the `public_token` and the institution they chose; after the session's lifetime expires, it reports expired instead of pending forever.
- **AC4**: Given a `public_token` from a completed Link session, when the agent calls the exchange tool, then it receives an `access_token` and `item_id` identifying that bank connection; the `access_token` never appears in server logs.
- **AC5**: Given a valid `access_token`, when the agent asks for accounts with "refresh balances" off (default), then it gets the accounts and their last-known balances quickly from Plaid's cache; with "refresh balances" on, it gets a live balance check against the institution (slower, and may fail with a retryable upstream error if the institution is temporarily unavailable).
- **AC6**: Given a valid `access_token` and no prior sync cursor, when the agent calls the transactions-sync tool, then it receives the available transaction history as "added" plus a cursor; calling again with that cursor later returns only what changed since then (added/modified/removed), not the whole history again.
- **AC7**: Given two different callers' credentials in concurrent requests, when both call any tool at the same time, then neither caller's access token, account data, or Plaid credentials become visible to the other caller — this must hold at the tool/API layer (there is no UI to hide things behind in an MCP server).
- **AC8**: Given an `access_token` for an Item that was never linked with Investments or Liabilities enabled, when the agent calls the holdings or liabilities tool for it, then it gets a structured, non-crashing error explaining the product is not enabled for that Item, not a stack trace or an opaque 500.
- **AC9**: Given the remove-item tool is called without explicit confirmation, when the agent attempts it, then the tool refuses and states that confirmation is required; given explicit confirmation and a valid `access_token`, the Item is removed and a subsequent call against that same `access_token` reports the Item no longer exists.
- **AC10**: Given Plaid responds with a rate-limit error, when a tool is mid-call, then the client retries with backoff (honoring `Retry-After` when present) within the shared per-call time budget, and only reports a retryable error to the agent if retries are exhausted — it never silently hangs past the budget.

### Open questions

- [NON-BLOCKING] Should a later version add the Transfer/Payments product (money movement) or Income? — No signal in the ticket that this is wanted now; left out of scope per Non-goals above. Not blocking: this version covers read-only financial data plus Link/Item lifecycle, which is itself a complete, shippable capability.
- [ASSUMED] The ticket does not say whether end customers' bank links already exist (access tokens already issued elsewhere) or need to be created through this MCP. This design assumes both: the agent can either operate on an existing `access_token` supplied by the caller, or create a new one through Hosted Link + exchange. If the real need turns out to be "read-only against tokens issued by another MSPbots system, Link/exchange never used," the create-link-token and exchange tools (AC1, AC3, AC4) are simply unused — no section needs to be redone if this assumption is wrong, so it is not marked blocking.

## Tech design

### Conclusion

Build `MSPbotsAIFramework/plaid-mcp` as a new, from-scratch Python 3.12 + `uv` + FastMCP Streamable-HTTP server (main line A), following the same stateless/multi-tenant/header-credential shape every other first-party MCP in this org uses (`hudu-mcp` read as the reference layout — see below). The one Plaid-specific wrinkle is that Plaid's access model is two-tier: app-level `client_id`/`secret` (how *we* authenticate to Plaid) plus a per-end-customer `access_token` (which bank connection — "Item" — a call is about). The header convention is for the former; the latter travels as an ordinary tool argument on every data-reading tool, because a single MSPbots tenant (one `client_id`/`secret`) manages many end customers' Items, and the server holds no state between calls to remember which `access_token` belongs to which conversation.

### Option analysis

| Option | What it does | Pros | Cost | Verdict |
|---|---|---|---|---|
| Hand-rolled `httpx` client (same shape as `hudu-mcp`'s `api_client.py`) | Thin per-request client built from the caller's own `client_id`/`secret`/env; explicit status→error mapping | Matches the house convention already in use by every other first-party MCP here; full control over retry/backoff/error-envelope shape; no new dependency beyond `httpx` (already standard) | Have to hand-map Plaid's ~29 `error_type` values into the fixed MCP error vocabulary (see Data & API contract) | **Chosen** |
| Official `plaid-python` SDK | Generated client wrapping Plaid's OpenAPI spec; one `ApiClient`/`Configuration` object per call | Plaid-maintained, always matches the current API surface, saves hand-writing request/response shapes | `Configuration` is designed to be built once and reused; building a fresh one per request to keep multi-tenant isolation airtight works but fights the SDK's intended usage pattern; adds a sizeable generated-code dependency and its own type surface on top of the one this org's MCPs already standardize on (`httpx` + hand-rolled models) | Not chosen: marginal benefit does not offset diverging from the fleet-wide pattern, on a repo with no existing code of its own to defer to |

No existing code in *this* repo to be consistent with (empty scaffold) — the tie-break is the org-wide house style observed in `hudu-mcp`, not an in-repo precedent.

### Data & API contract

**Credential headers** (declared in README, read verbatim in `middleware.py`):

| Header | Required | Meaning |
|---|---|---|
| `X-Plaid-Client-Id` | yes | Plaid developer `client_id`, from the Plaid Dashboard |
| `X-Plaid-Secret` | yes | Plaid developer `secret` matching the environment below |
| `X-Plaid-Env` | yes | `sandbox` or `production` (Plaid retired the separate "development" environment; only these two base URLs exist today: `sandbox.plaid.com`, `production.plaid.com`) |

Missing or empty any of the three → 401, body lists all three header names (never echoes back what was sent).

**Tools** (11; all return a JSON string; truncated lists carry `has_more`):

1. `plaid_create_link_token(products: list[str], client_user_id: str, hosted_link: bool = true, delivery_method: str | None = None, redirect_uri: str | None = None) -> {"link_token": str, "hosted_link_url": str | None, "expiration": str}` — calls `POST /link/token/create` with `hosted_link: {}` (or `{"delivery_method": ..., "completion_redirect_uri": ...}`); `readOnlyHint=false` (creates a session), `idempotentHint=false`.
2. `plaid_get_link_session(link_token: str) -> {"status": "pending"|"completed"|"expired", "public_token": str | None, "institution": {...} | None}` — calls `POST /link/token/get`, maps its session-completion metadata.
3. `plaid_exchange_public_token(public_token: str) -> {"access_token": str, "item_id": str}` — calls `POST /item/public_token/exchange`; `destructiveHint=false`, `idempotentHint=false` (each call against the same `public_token` after the first fails — Plaid tokens are single-use).
4. `plaid_get_item(access_token: str) -> {"item_id": str, "institution": {...}, "available_products": [...], "billed_products": [...], "consent_expiration_time": str | None, "error": {...} | None}` — `POST /item/get`.
5. `plaid_remove_item(access_token: str, confirm: bool) -> {"removed": true}` — `confirm != true` → `invalid_argument` envelope explaining confirmation is required, **no call made to Plaid**; `destructiveHint=true`.
6. `plaid_get_accounts(access_token: str, account_ids: list[str] | None = None, refresh_balances: bool = false) -> {"accounts": [...]}` — `refresh_balances=false` → `POST /accounts/get`; `true` → `POST /accounts/balance/get` (slower, live check).
7. `plaid_get_auth(access_token: str, account_ids: list[str] | None = None) -> {"accounts": [...], "numbers": {"ach": [...], "eft": [...], "international": [...], "bacs": [...]}}` — `POST /auth/get`.
8. `plaid_sync_transactions(access_token: str, cursor: str | None = None, count: int = 100) -> {"added": [...], "modified": [...], "removed": [...], "next_cursor": str, "has_more": bool}` — `POST /transactions/sync`; `count` clamped 1–500.
9. `plaid_get_identity(access_token: str, account_ids: list[str] | None = None) -> {"accounts": [...]}` — `POST /identity/get`.
10. `plaid_get_investments_holdings(access_token: str, account_ids: list[str] | None = None) -> {"accounts": [...], "holdings": [...], "securities": [...]}` — `POST /investments/holdings/get`; Item without Investments enabled → `invalid_argument` envelope (Plaid's `INVALID_PRODUCT`), not a crash.
11. `plaid_get_liabilities(access_token: str, account_ids: list[str] | None = None) -> {"accounts": [...], "student": [...], "credit": [...], "mortgage": [...]}` — `POST /liabilities/get`; same not-enabled handling as above.

**Error envelope** (all tools, never an uncaught exception):

```json
{"error": {"code": "invalid_argument", "message": "Investments is not enabled for this Item. Re-link with the investments product to use this tool.", "retryable": false}}
```

`code` is one of the fixed six (`not_configured`/`unauthorized`/`not_found`/`invalid_argument`/`rate_limited`/`upstream_error`). Mapping from Plaid's `error_type` (29 values; `causes` array for multi-item batch errors, not used here since every tool is single-Item):

| Plaid `error_type` | MCP `code` | `retryable` |
|---|---|---|
| `INVALID_REQUEST`, `INVALID_INPUT`, `INVALID_PRODUCT` | `invalid_argument` | false |
| `RATE_LIMIT_EXCEEDED` | `rate_limited` | true (honor `Retry-After` if present) |
| `ITEM_ERROR` with `error_code = PRODUCT_NOT_READY` | `upstream_error` | true |
| `ITEM_ERROR` (other codes, e.g. `ITEM_LOGIN_REQUIRED`) | `invalid_argument` | false (needs re-link, not a retry) |
| `INSTITUTION_ERROR` | `upstream_error` | true |
| `API_ERROR`, HTTP 5xx with no parseable body | `upstream_error` | true |
| `OAUTH_ERROR`, `PAYMENT_ERROR` | `invalid_argument` | false |
| HTTP 401/403 from Plaid itself (bad `client_id`/`secret`) | `unauthorized` | false |
| connection error / timeout | `upstream_error` | true |

**Backward compatibility**: new repo, no existing tenants depend on a prior tool/header shape — nothing to stay compatible with yet. Future tool/param changes follow SOP §13 (breaking vs. compatible) starting from this version's `tools/list` snapshot.

### Key flow / sequence

Linking a new bank account end-to-end (the only multi-step flow; every other tool is a single request/response):

```
Agent                         plaid-mcp                              Plaid
  | create_link_token -------->  |
  |                               | POST /link/token/create (hosted_link) --> |
  |                               | <---------------------- link_token, hosted_link_url |
  | <--- hosted_link_url ---------|
  |  (agent/operator sends hosted_link_url to the end customer out of band)
  |                                                   end customer completes Hosted Link in their own browser
  | get_link_session(link_token)->|
  |                               | POST /link/token/get -------------------> |
  |                               | <----------------------- status, public_token (once completed) |
  | <--- status/public_token -----|
  | exchange_public_token ------->|
  |                               | POST /item/public_token/exchange --------> |
  |                               | <----------------------- access_token, item_id |
  | <--- access_token, item_id ---|
  (agent stores access_token itself; every later data tool call passes it back in)
```

### Non-functional

- **Idempotency & concurrency**: one shared `httpx.AsyncClient` per process; every credential (`client_id`/`secret`/`env` from headers, `access_token` from the tool argument) travels only through the call stack of its own request — no module-level or cross-request caching of either. `plaid_exchange_public_token` and `plaid_create_link_token` are not idempotent by nature of Plaid's own API (single-use `public_token`, fresh `link_token` each call) — this is Plaid's contract, not something this server can or should paper over; documented in the tool descriptions.
- **Performance**: `count`/`limit` on every list-shaped tool clamped to Plaid's own ceilings (`transactions/sync` ≤ 500); compact (non-pretty) JSON, `ensure_ascii=False`; connect/read timeouts 5s/30s, ≤ 2 retries, whole-call budget under the shared 120s gateway timeout (100s, same margin as `hudu-mcp`).
- **Security**: `access_token`, `client_id`, `secret`, account/routing numbers, and identity PII are never written to logs — request logging records method/path/status/duration only (same shape as `HuduClient`'s `logger.info` line), never the request or response body. `PlaidCredentials.__repr__` redacts `secret`. `gitleaks detect` run before the first commit to `main` and again before every subsequent merge.
- **Multi-tenant isolation**: the three credential headers plus the per-call `access_token` are the *entire* identity of a request; nothing about one caller's Item, balances, or transactions can leak into another caller's response because nothing is ever stored between calls (AC7). This is the same isolation contract every other MCP server in this org makes, just with one extra per-call identifier (`access_token`) instead of only headers, because Plaid's own model has two tiers of credential.
- **Observability**: one log line per upstream Plaid call (method, path, status, duration, attempt count) — same shape as `hudu-mcp`'s `api_client.py`. No request/response bodies logged, ever (see Security above — this is financial PII).

### Rollout & rollback

New repo, new vendor — no existing traffic to protect. First version is pushed straight to `main` (SOP A2: "new repo, no one depends on it yet"), then registered with the INT gateway via `/api/vendor-register` (new-vendor path, not `/api/deploy-int`) once self-test passes. Rollback is "stop sending this vendor traffic at the gateway" (a gateway/platform action, out of this repo's reach) — there is no in-repo feature flag because every tool here is read-only against data that already exists except `plaid_remove_item`, which requires explicit `confirm=true` and cannot be triggered by a stray retry (Plaid's own single-use-token semantics already force each Link/exchange call to be deliberate).

### Risks & dependencies

- **Risk**: Plaid Sandbox's simulated data may not exercise every field this design expects from Investments/Liabilities (narrower test-institution coverage than Transactions/Auth) — mitigated by marking those cases "needs a real vendor account" in the self-test report rather than blocking; the tool's structured-error path (AC8) is what actually matters for correctness here, and that *is* sandbox-testable (link an Item without the product, call the tool, confirm the structured error).
- **Risk**: Production access requires Plaid's standard approval step (their own underwriting/compliance review for live bank data) — out of this repo's control and not needed to build, test, or publish this version to INT (Sandbox is sufficient); flagged so whoever eventually connects a real tenant knows Production is a separate approval step on Plaid's side, not a flag in this server.
- **Dependency**: none on another ClickUp ticket or another MSPbotsAIFramework repo. `mcp-service-gateway` is read-only reference for understanding how credentials reach a vendor MCP in general; no gateway change is requested or needed here.

## Decisions made by DEV01

- **`access_token` travels as a tool argument, not a header.** Reasoning: the three credential headers identify *who is calling* (one MSPbots tenant's Plaid developer account); `access_token` identifies *which end customer's bank connection* a given call is about, and one tenant manages many end customers' Items through the same `client_id`/`secret`. A header can only carry one value per request path in this convention, and putting `access_token` there would mean one MCP connection could only ever address one end customer at a time. Alternative not chosen: a fourth header `X-Plaid-Access-Token` — rejected because it would force a new MCP "session"/header-set per end customer, which doesn't fit how an agent conversation naturally spans multiple customers' accounts in one sitting.
- **Hosted Link only, no embedded Link SDK support.** Reasoning: this server has no UI and cannot embed Plaid's client-side JS/mobile SDK; Hosted Link is Plaid's own server-only, no-SDK integration path built for exactly this shape of integration. Alternative not chosen: requiring the caller to run Link themselves and only exchange the resulting `public_token` here — rejected because then this MCP would do nothing to help an agent *initiate* a new connection, only consume one already created elsewhere, which seemed like a strictly smaller and less useful version of the same tool.
- **No webhook receiver; discovery is poll-based (`plaid_get_link_session`, `/transactions/sync`'s own cursor).** Reasoning: the MCP service is not publicly reachable (same constraint as every other first-party MCP here), so Plaid cannot call back into it regardless of preference. `/transactions/sync`'s cursor model already makes "poll periodically" a first-class, efficient pattern (unlike `/transactions/get`), so nothing is lost by skipping webhooks for transactions; Hosted Link completion is explicitly designed by Plaid to support polling `/link/token/get` as an alternative to the webhook.
- **`plaid_get_accounts` folds `/accounts/get` and `/accounts/balance/get` into one tool with a `refresh_balances` flag**, rather than two separate tools. Reasoning: SOP A4 asks to merge overlapping tools; the two Plaid endpoints return the same account/balance shape and differ only in "cached vs. forced-fresh", which is naturally a boolean option on one tool rather than a second whole tool an agent has to know to reach for.
- **Investments and Liabilities included in the first version despite being the two sandbox-narrower products.** Reasoning: the ticket's own generic template promises "live access" with no capability named, so scope was set by "what Plaid itself documents as a core read product" rather than guessing a narrower list; if real usage never touches these two, they cost nothing extra to have shipped (SOP's "default read-only" posture makes an unused read tool inert, not risky).
- **Did not use the official `plaid-python` SDK.** See Tech design → Option analysis.

## Test cases

(Pass/fail statements live here; full steps, preconditions, and evidence fields are in the sibling `PRD-21315.ac.json`.)

- **TC1** (AC1, automated): Given valid headers and `products=["transactions","auth"]`, `plaid_create_link_token` returns a non-empty `hosted_link_url` and `link_token`.
- **TC2** (AC2, automated): Given a request with `X-Plaid-Secret` omitted, any tool call returns HTTP 401 and an error body listing all three required header names, none of them containing the (absent) secret value.
- **TC3** (AC3, automated — sandbox): Given a `link_token` whose session has not completed, `plaid_get_link_session` reports `status="pending"` and no `public_token`.
- **TC4** (AC3, manual/needs a real vendor account): Given a Hosted Link session completed by a human tester in a browser, `plaid_get_link_session` reports `status="completed"` with a `public_token` and institution name.
- **TC5** (AC3, automated — sandbox): Given a `link_token` created with a very short `url_lifetime_seconds` that has since elapsed, `plaid_get_link_session` reports `status="expired"`.
- **TC6** (AC4, automated — sandbox): Given a `public_token` from `/sandbox/public_token/create`, `plaid_exchange_public_token` returns a non-empty `access_token` and `item_id`; the access token value never appears in the server's stdout/log capture for that request.
- **TC7** (AC5, automated — sandbox): Given a valid `access_token`, `plaid_get_accounts(refresh_balances=false)` returns accounts with a `balances` object per account.
- **TC8** (AC5, automated — sandbox): Given the same `access_token`, `plaid_get_accounts(refresh_balances=true)` returns the same accounts via the live-balance endpoint (different underlying Plaid call, asserted via a request-count/path check against the stub in unit tests; sandbox call confirms the shape matches).
- **TC9** (AC6, automated — sandbox): Given a valid `access_token` and no `cursor`, `plaid_sync_transactions` returns a non-empty `added` list and a `next_cursor`.
- **TC10** (AC6, automated — sandbox): Given the `next_cursor` from TC9 with no new activity on the sandbox Item since, a second `plaid_sync_transactions` call returns empty `added`/`modified`/`removed` and `has_more=false`.
- **TC11** (AC7, automated): Given two concurrent requests with different `client_id`/`secret` pairs (both against stubbed upstream responses), the response to each carries only that request's own stub data; a shared in-process counter proves no state object is reused across the two contexts.
- **TC12** (AC8, automated — sandbox): Given an `access_token` for an Item linked only with `transactions` (not `investments`), `plaid_get_investments_holdings` returns an `invalid_argument` error envelope (not an exception) naming the missing product.
- **TC13** (AC8, automated — sandbox, same shape as TC12): Given an Item without `liabilities` enabled, `plaid_get_liabilities` returns the same class of structured error.
- **TC14** (AC9, automated): Given `plaid_remove_item(access_token=<valid>, confirm=false)` (or `confirm` omitted), the tool returns an `invalid_argument` error asking for `confirm=true`, and no request is sent to Plaid (asserted against the stub's call count).
- **TC15** (AC9, automated — sandbox): Given `plaid_remove_item(access_token=<valid>, confirm=true)`, the call succeeds and a subsequent `plaid_get_item` with the same `access_token` returns an item-not-found-shaped error.
- **TC16** (AC10, automated): Given a stubbed upstream that returns HTTP 429 with `Retry-After: 1` twice then succeeds, the client retries twice honoring the header and returns the successful result; total elapsed time is close to 2s, not more.
- **TC17** (AC10, automated): Given a stubbed upstream that returns HTTP 429 on every attempt, the client retries up to its cap and then returns a `rate_limited`, `retryable=true` error envelope rather than hanging past the call budget.
- **TC18** (not tied to a single AC, automated): `tools/list` returns exactly 11 tools with names matching the Data & API contract table; none has a description over 500 characters or a first line over 100.
